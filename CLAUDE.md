
## Database

SQLite via Prisma. DB file at `prisma/master.db`, URL from the `DATABASE_URL` env var, else that default (`databaseUrl()` in `src/db/client.ts`, the one place it is resolved). A relative `file:` path resolves against the repo root, never the working directory, so a server started from elsewhere cannot create a stray empty database. `prisma` and `dotenv` are runtime dependencies: every start may run `prisma db push`, which loads `prisma.config.ts`.

```bash
npx prisma generate               # Regenerate Prisma client (after schema changes)
```

**Schema changes apply themselves.** Every start of the CLI, the MCP server and the app server runs `prepareDatabase` (`src/db/prepare.ts`): `syncSchema` (`src/db/schema-sync.ts`) compares a fingerprint of `schema.prisma` with the one stored in the database's `PRAGMA user_version`, and on a difference backs the file up beside itself (`<db>.bak-<time>-schema`) and runs `prisma db push` against the URL the client was opened with; then `normalizeDates`. So a new table or column needs no step on any machine, and no code has to cope with it missing. A change that would lose data (dropping a column) is refused by db push, which fails the start with Prisma's message and leaves the database alone: run `npx prisma db push --accept-data-loss` by hand for those, on every machine. The one data step in `prepareDatabase` besides dates is `migrateSessionSizes` (`src/db/session-sizes.ts`), which moves a Config row still on the old session defaults (5 new + 15 reviews, later 20 + 20) to 30 + 30. Don't use `user_version` for anything else; `db:dump` carries it over so a restored database doesn't push again.

Tests use isolated temp SQLite databases created per test suite in `__tests__/setup.ts`, built through `syncSchema` like a real start. They call `setDb()` to inject the test client — production code accesses the DB via `getDb()` from `src/db/client.ts`. Vitest globals are off: import `describe`/`it`/`expect` from `"vitest"`. `setup.ts` sets `FLASHCARD_EMBEDDINGS=off` (inherited by the CLI tests' children), so no test loads the embedding model, and every fork worker preloads `__tests__/exit-with-runner.mjs`, so a worker whose runner died (`vitest run | head` kills it) exits instead of living on and filling memory. Still, run the suite to a file rather than into `head`.

## Architecture

Three adapters share one SDK, which is the only way into the core library:

```
CLI (src/cli/index.ts)  ──┐
MCP (src/mcp/server.ts) ──┼── SDK (src/sdk/index.ts) ── Core services (src/core/*) ── Prisma/SQLite
App (src/app/server.ts) ──┘
```

**The SDK** (`src/sdk/index.ts`) is a facade: it re-exports the core functions the adapters use (and `openDeck()`, which opens the database and runs `prepareDatabase`), so an adapter imports from `../sdk/index.js` and from nowhere deeper (`__tests__/sdk/boundary.test.ts` fails on a `../core/` or `../db/` import in `src/mcp`, `src/app` or `src/cli`). Adapters translate transport only; every rule and every query lives below. A new capability is a core function, exported from the SDK, then a one-line adapter method. **Nothing outside this repo opens master.db**: the study repo's anki-sync, card-quality gate and sweep, the wiki-viewer and Omvida reach the deck through the app server (below), whose plain-data methods exist for them.

**The app server** (`src/app/`) is the Omvida desktop app's connection (`~/Code/omvida`): newline-delimited JSON over stdio, `{id, method, params}` in and `{id, result|error}` out, plus a `{"ready": true}` line at start. Not MCP, which would make a QML client implement the handshake and result envelopes for nothing it needs; not the CLI per call, because each start costs about a second. `handlers.ts` is a thin method table (the /study loop's tools reshaped for a GUI) that never touches Prisma itself, and differs from the MCP tools in these deliberate ways: `startSession` derives `maxNewCards` from the pressure verdict itself (`backlogNewCap`: ok → default, warn → 3, pause → 0, /study's Phase 2 table; a share ahead keeps `backlogHoldsNewBack`, 0 at warn too), and with `ahead: true` studies ahead on a rest day (study-ahead.ts); `nextCard` returns a leech block as data (`{blocked: {card, lapses}}`, from core `getNextCardOrBlock`) instead of throwing, since a GUI needs the card to show the ways out; `nextCard` also carries `schedules`, what each rating would schedule (`previewSchedules` in session-service, the same FSRS step and intra-day rule as `submitReview`), for the app's rating keys; `grade` suggests a rating (grading.ts); and `undoReview` takes the session's newest review back (app-only: /study has no keys to undo with), `review` with the same rating being its redo. `stamp` comes from `changeTokens()` (`src/core/change-tokens.ts`). `src/core/overview.ts` builds the progress picture (pressure, calibration, streak, maturity over unsuspended cards so the buckets sum to `totalCards`, the last seven local days of reviews, `load` (the review chart around today from `loadBars`: five study days each side, then 2, 4 and 8 study-day totals; rest days are left out, columns and totals alike), pending review cards, and on a rest day `ahead`, the share it offers to study ahead) that both the app and `master overview` (the bar widget's source) print; it passes the pressure and calibration verdicts through whole, never recomputing them. Requests run concurrently, so a grade never holds up a page of cards.

**Plain-data app methods** serve callers that are not Omvida (all datetimes ISO-8601 UTC strings, null stays null): `cardRecords {ids?, inheritedFrom?, includeSuspended?=true}` (whole cards, no embedding: `core/card-records.ts`), `reviewRecords {cardIds?}`, `tombstones` (ids of deleted cards), `calibration` (exactly `checkCalibration`'s report), `deckOverview` (`core/deck-overview.ts`: unsuspended totals, deck count, count per state) and `syncApply {schedules?, reviews?, imports?, deletions?, schedulerOptions?}` (`core/sync-apply.ts`, one transaction applying an anki-sync plan). `applySync` is where Anki's side meets this deck's invariants: a pulled schedule never leaves a non-New card at stability 0 (`fallbackMemoryState` in scheduler.ts, beside `sanitizeForReview`) and never touches `updatedAt`; reviews append once per (card, whole second) with `elapsedDays` from the card's previous review (the ones left out are counted in `reviewsSkipped: {present, noCard}`); an import keeps the Anki guid as the card id, runs the content rules and reports `rejected: [{id, error}]` per card instead of failing the batch; a deletion goes through the tombstone and Prisma's cascades like `deleteCard`; `schedulerOptions` writes only the Config columns that changed.

**Maturity is derived, never stored.** Call `cardMaturity(card)` (scheduler.ts) at the point of display. A stored column once existed; it was set at creation and never updated on review, so it reported cards with 38 reps and 2229 days of stability as `new`.

**Day boundaries are local.** Every day key (streak, intake, the overview's week, calibration's one-review-per-card-per-day rule) comes from `src/core/days.ts` (`localDay`, `startOfLocalDay`, `MS_PER_DAY`), never from UTC dates. The one exception is `Review.elapsedDays`, a UTC calendar-day difference (`dateDiffInDays`, taken in `reviewCard` since ts-fsrs 6 no longer reports it), which calibration's `elapsedDays >= 1` filter keeps deliberately (documented on `eligibleReviews`).

**Core modules** (`src/core/`):
- `scheduler.ts` — ts-fsrs wrapper (v6, FSRS-6 through the legacy `fsrs()` facade, which supports learning steps). Pure functions, no DB. `reviewCard()` applies a rating under `SchedulerParams`: request retention, learning and relearning steps and FSRS weights, all from `Config` (`schedulerParams()` in session-service, which `submitReview` and `previewSchedules` use). Those four Config columns, `easyDays` and the daily limits (`newPerDay`, `reviewsPerDay`, `newCardsIgnoreReviewLimit`, which `startSession` applies on top of its per-session caps, counting today's cards as Anki does: new if today holds their first review; due reviews the limit keeps out come back as `reviewsHeldBack`, which the app shows) are mirrored from the Anki deck options by the study repo's `anki-sync` (through `syncApply`'s `schedulerOptions`), so the rating keys show Anki's intervals; `avoidEasyDays` applies Anki's Easy Days as a deterministic weekday rule within the fuzz range (no load balancing, no randomness, so preview still equals review); it runs at review time only, so `easy-days.ts` (`rescheduleEasyDays`, the CLI's `easy-days`, a dry run without `--apply`) applies it once to reviews already scheduled, with each card's last elapsed days, changing only `due` and `interval`; defaults are Anki's (steps `1m,10m` / `10m`, 0.9, library weights). A card's `learningStep` is its place in the steps. Fuzz is off on purpose: preview and review run at different moments, so a fuzzed preview would promise an interval the review doesn't give. A New card's memory is normalized to 0/0 and a lower-than-1 difficulty clamped before a review, since ts-fsrs 6 throws on both. `getRetrievability()` returns recall probability, `cardMaturity()` derives new/learning/familiar/internalized from `state` + `interval` (mature at `MATURE_INTERVAL_DAYS`, Anki's 21-day convention). Uses `Grade` type from ts-fsrs (not `Rating` — `Grade` excludes the `Manual` variant); `isGrade()` is the one check that a rating is 1–4. Import `State`/`Rating`/`Grade` from ts-fsrs directly.
- `rest-days.ts` — Rest days and studying ahead on them, the pure rules. A rest day is a weekday Easy Days set to Minimum (0), so Anki stays the one place the week is set. `startSession` brings no new cards on one; what a rest day offers instead is studying ahead: `aheadShare` is a seventh (`AHEAD_SHARE_DAYS`) of what is left of the week (`weekAhead`: from tomorrow past rest days, through the study days up to the next rest day), the reviews due by then and the new cards those days would bring in, in that mix, fixed for the day (what today studied is counted in and taken off, so a finished share offers nothing more). New cards studied on rest days are borrowed: `borrowedToday` takes them off the first study day's limit after the rest days, then the next once that one is used up (`restRunBefore`).
- `study-ahead.ts` — The counts those rules take, from the deck, and the cards a share picks (`planAhead`): learning steps due now (never limited), then Review cards due before the week ends, lowest retrievability first (long intervals near their day, where an early review costs FSRS least; a card studied today is not picked again), then the oldest new cards; `newBorrowedToday` for `startSession`'s limit on a study day. The share's reviews today are reviews of Review cards (`Review.state`), never learning steps, and a card studied today counts there only, not again in what is left, so the share stays fixed; with every day a rest day there is no week and no plan. The overview's plan caps new cards by the backlog as sessions do (`backlogHoldsNewBack` in pressure.ts, one rule for both). It takes the settings as arguments, so it never reads Config; `session-service`'s `currentAheadPlan` and `startSession({ ahead: true })` (no session caps, no category or deck; it throws on a study day) call it. Anki-sync needs nothing for it: a review ahead is a newer review, so its schedule and revlog row push to Anki.
- `card-records.ts`, `deck-overview.ts`, `sync-apply.ts` — The plain-data readers and the sync writer behind the app server's non-Omvida methods (see "Plain-data app methods").
- `card-service.ts` — Card CRUD, duplicate detection (Jaccard + semantic embeddings), `findSimilar()`, `getDueCards()`/`countDueCards()`, `listCards()`/`searchCards()`/`allCards()` (tags match exactly; return the deck name, and omit the `embedding` column). Every deletion (`deleteCard`, `deleteCards`, `deleteDeck`) writes a `DeletedCard` tombstone through `tombstone()`, so the external anki-sync can tell a local delete from a card created elsewhere.
- `deck-service.ts` — Deck CRUD; `listDeckStats()` gives every deck's counts in 3 queries total.
- `exercises.ts` — Code cards: a card answered by running it, after Execute Program. Three kinds (`predict`, `fill`, `compose`), one JSON format in `Card.exercise` (`parseExercise` reads a broken or wrong-shaped column as no exercise, so one bad row can't fail a listing), from which `front` and `back` are written, so every other reader of a card needs nothing new. Answers are compared by value in a real interpreter, so equivalent answers pass. A pass rates Good and giving up rates Again, whatever the tries (`PASS_RATING`, `GIVE_UP_RATING`); no Claude call. `checkExercise` is the dry run behind `check_code_card` and every write: the solution passes, its blanks left nil don't, two runs agree. A predict card keeps real values hidden until it passes.
- `exercise-sandbox.ts` — Runs that code under bubblewrap: no network, read-only system, no home, a clean environment (this process holds the API key, so bubblewrap itself starts without it), a timeout, limits on memory, processes and file size, a size for each place a file can go (`/tmp`, `/dev/shm`; the rest of `/dev` is read-only), and an output cap. About 60 ms a run for Ruby, Python and JavaScript, about half a second for TypeScript and two for Postgres. The app server's `runExercise` stops the run before it, so an endless loop being typed keeps one process, not one per pause. The verdict comes back on fd 3, so nothing printed can forge it.
- `exercise-runners.ts` — What differs per language (`LANGS`: ruby, python, javascript, typescript, postgres): the interpreter, the harness that evaluates the source and each case and compares values the language's own way, the comment a card's sides show goals after, and what an empty blank holds. Ruby and Python are found through `mise which`, then the PATH past mise's shims (`FLASHCARD_RUBY`, `FLASHCARD_PYTHON` override); JavaScript, TypeScript and Postgres run on the server's own Node (`FLASHCARD_NODE`). TypeScript is type-checked with `tsc --strict` before any case runs, and a type error is the run's `error`, like a Ruby syntax error. Postgres is PGlite (Postgres as WASM, empty per run): a case's `expr` is one query and its `goal` the rows as an array of row arrays, each case rolled back after. It starts from an empty database made once per PGlite version (`~/.cache/flashcard-mcp/pglite-<version>.tar`, 40 MB, built on the first run and mounted read-only): 0.4 s a run instead of 1.6. `typescript` and `@electric-sql/pglite` are runtime dependencies for that reason. A new language is one `case` in `runnerFor`, a harness that writes `{error, cases}` to fd 3, and its tests in `exercise-runners.test.ts`.
- `cloze.ts` — `{{c1::...}}`, on code cards only: `validateCardContent` refuses a cloze on any other card, on every write and import, including inside `<pre>`. Always c1: Anki makes a card per number and anki-sync keeps one schedule per note. `clozeSides` gives what the app shows; `ankiClozeText` keeps code from breaking Anki's parser (`}}`, `::`). A card keeps its kind (plain, cloze, code) for life, as an Anki note keeps its note type: `assertSameAnkiShape`. The MCP's `create_code_card`, `update_code_card`, `check_code_card`, `run_code_card` and `reveal_code_card` are the skills' way in; the app's are `runExercise` and `revealExercise`.
- `content-rules.ts` — `assertCardContent()` gates every create/update: fields are simple HTML (markdown is rejected, Anki shows it literally), no em dashes, fronts ask a single question, answers capped at `MAX_ANSWER_CHARS` and a sentence count, both measured on rendered text; `visibleText()` for display.
- `session-service.ts` — Study session lifecycle. An open session's queue and position are saved in `StudySession.queueState` (JSON) on every change and cached per process, so a session survives a restart of the MCP server or the app server and any process can resume it; one process drives a session at a time. `endSession` and an exhausted queue clear it. Session size: due reviews up to `maxReviewCardsPerSession` (the `Config` row, schema default 30; the row is created on first read), then new cards filling the session up to that size and never fewer than `MIN_NEW_PER_SESSION` (3), so 30 due make 30 + 3 and 8 due make 8 + 22; `maxNewCardsPerSession` (default 30) only caps that fill, and the day's `newPerDay` caps it, floor included. `startSession` filters by `category` and/or `deckId` (both also bound new-card top-ups) and returns `newCount`/`reviewCount`. A card deleted mid-session is replaced by a new card only while the session's new allowance lasts (`SessionState.newRoom`: its limit less the new cards it queued, a deleted new card giving its place back), so a delete never brings a new card on a rest day or past what one borrowed. `submitReview` records the card's state before the review in `Review.state` (Anki's revlog `type`, which anki-sync carries both ways; null on older rows). `submitReview` writes the card, the review and the session in one transaction and throws, writing nothing, when the session isn't open (ended, exhausted, unknown) or the card isn't the one at the queue's pointer (a retried submit would schedule it twice and pass the next card over; undo restores the pointer, so a redo passes). `undoLastReview` takes the newest review back, again and again (the app's Ctrl+Z): card scheduling and leech fields, the review row, the session's counters and queue, reopening an ended session; it keeps the snapshots in memory (a record is dropped only once its transaction succeeded, so a busy database leaves the rating undoable), for this process and until the next `startSession`, and lifts an unanswered leech flag on a card still to come, which its serve stamps again. Accuracy is Good/Easy over reviews submitted, so skips don't count. **`endTime` means "the session was ended" — `submitReview` does not touch it**, nor the card's `updatedAt`, which means "the content was edited" (the app server's `stamp` counts reviews apart), so a null `endTime` is a session that was never closed rather than one that is merely idle. Close with `endSession()` (idempotent; returns a `SessionSummary` with ISO dates; the `end_session` MCP tool). `startSession()` first discards sessions that reviewed nothing, since those carry no information; sessions that did review cards are left open rather than back-stamped, because inventing an end time would invent a duration. 
- `embeddings.ts` — Two-stage similarity: `jaccardSimilarity()` (always available) + `cosineSimilarity()` on 384-dim vectors from `@huggingface/transformers` (lazy-loaded, ~30s first call; a failed load is not retried per call). `findSimilarCards()` accepts optional `SemanticOptions` for the embedding stage. Thresholds are the named constants here (see Duplicate detection).
- `pressure.ts` — SRS pressure: two axes (review backlog excluding state-New cards, cards added today) with warn/pause thresholds. `dueReviewWhere()` is the one backlog predicate (pressure, `startSession`, overview) and `NEW_CARD_WHERE` the one new-card pool (unsuspended state New, whatever its `due`; pressure's `newAvailable` and session top-ups). `checkPressure()` backs the `check_pressure` tool; `backlogNewCap()` is the cap the backlog puts on a session's new cards (none at ok, `MIN_NEW_PER_SESSION` = 3 at warn, 0 at pause); `assertCanCreateCard()` gates `createCard` at pause (`inheritFrom` creates and `updateCard` are never gated). New cards are an optional pool, never backlog; the cards-added-today axis uses the local calendar day (days.ts). Splits are excluded from intake via the `Card.inheritedFrom` column, set by `createCard` when `inheritFrom` is passed; imported cards created today do count. `clearance` covers the flashcards axis only — reviewing cannot lower intake, only the next day resets it. Batch writers that check pressure once up front pass `skipPressureGate` so an import is refused atomically rather than aborting half-applied (see `importCards`). Two entry points by cost: the internal `checkPressureCore()` is two counts flat and backs the create gate, while `checkPressure()` adds `newAvailable` and the per-deck breakdown (`listDeckStats`), 7 queries in all. Keep the gate on the core — it runs on every fresh card and reads none of the extras.
- `leeches.ts` — Leech enforcement, in the same spirit as the pressure gate: `getNextCard` stamps `Card.leechFlaggedAt` on a served card with `LEECH_LAPSES` (5) or more lapses and refuses to serve another until the flag is answered — `update_card` (clears the flag and resets lapses to 0), a split via `create_card` with `inheritFrom` plus `delete_card`, a plain `delete_card`, or `deferLeech` behind the `resolve_leech` tool. A deferral records `Card.leechDeferredLapses` and flags again at the next failure. Suspended cards are never flagged, and `inheritFrom` copies neither the flag nor the lapse count off a flagged parent.
- `card-notes.ts` — Card notes: what the developer noted about a card mid-study (Omvida's Ctrl+N) to handle later in one fix session, free markdown, one per card (`CardNote`, cascade-deleted with the card). A table rather than a Card column, so a note never moves `Card.updatedAt`. `setCardNote` (empty body deletes), `listCardNotes`, `resolveCardNote` (the `resolve_card_note` tool, after the fix). Nothing here edits the card itself. The app server's `stamp` counts notes too, and `sessions` (`src/core/recent-sessions.ts`) lists recent sessions with the cards each lapsed and noted, by time window, since reviews carry no session id.
- `analytics-service.ts` — `getFullStats()` aggregates streak, retention, maturity, lapses in parallel. The streak counts consecutive local days with at least one review (`Review.reviewedAt`), not session starts.
- `grading.ts` — Suggested ratings for typed answers, from the Claude API (`@anthropic-ai/sdk`, `claude-haiku-5-5`, structured output against `GRADE_SCHEMA`, effort low, thinking left adaptive; a declined grade is asked of `claude-sonnet-5-5` once, since Haiku has no server-side refusal fallback). No tools: it judges against the card back alone. The rubric in `GRADE_SYSTEM_PROMPT` is /study's and is **fixed**: the ratings produce the true-retention number that tunes difficulty, so the rubric must not move with it. It only rates: the card-quality flags it gave until 2026-10-31 moved to the study repo (a write-time gate hook, and `/study-card-check` on Omvida's Ctrl+Q). It only suggests: nothing here writes, and `submitReview` takes whatever rating the developer chose. The key comes from `ANTHROPIC_API_KEY` (Omvida's `bin/omvida-deck` reads it from the login keyring); with none, the server starts and each grade says so. The app server's `Grader` runs at most one grade: a newer `grade` aborts the one still running, claiming its slot on arrival so requests keep their order; `nextCard` and `endSession` abort the last card's grade. The API call is injected for tests (`GradeCall`). It ran on `claude -p` until 2026-10-30 (~3s a grade), then on Sonnet; Haiku since 2026-10-31 (same pass/fail as Sonnet on 28 of 30 real cards), about $0.00015 a grade.
- `db-dump.ts` — Portable SQL dump/restore behind `db:dump`/`db:restore`. A restore builds the database in `<db>.restoring` and renames it over the target only after the whole dump ran, so a broken dump with `--force` leaves the existing database untouched.
- `days.ts`, `version.ts` (`PACKAGE_VERSION` from package.json, reported by the CLI and the MCP server), `types.ts` (shared types, `CARD_STATE_NAMES`, `parseTags()`/`serializeTags()`).

**MCP server** exposes 32 tools. `src/mcp/server.ts` exports `createServer()` and starts only when run directly, exiting 1 when start-up fails. Tool arguments are validated by `McpServer` against each tool's Zod `inputSchema`; every tool error is a thrown error, which the SDK turns into an `isError` result. Its tests (`__tests__/mcp/server.test.ts`) drive the real tools through the SDK's `InMemoryTransport`. Card import and export (`.apkg`, `.txt`) no longer exist: cards reach Anki through the study repo's `anki-sync`, which writes this deck through `syncApply`.

**Skills** (in `~/.claude/skills/`):
- `/study` — Interactive review sessions. Claude evaluates answers and rates them.
- `/study-flashcard` — Create SRS flashcards directly: suggests a few ready fronts, the developer picks, they are created after semantic duplicate detection.

## Key Design Decisions

**Anti-overload:** Never auto-generate cards. Drafts require explicit approval. Default 2-3 cards per creation session. Practice-first mode prioritizes exercises over flashcards.

**Internalized cards:** Stay active at lower review frequency (FSRS stability handles natural spacing). Never removed; "internalized" is derived by `cardMaturity()` (Review state, interval ≥ `MATURE_INTERVAL_DAYS`).

**Duplicate detection:** Two-stage — Jaccard word-overlap on fronts (fast, always on) then cosine similarity on front+back embeddings (requires `initEmbeddings()` first load). Thresholds (`embeddings.ts`): `createCard` warns at Jaccard ≥ `JACCARD_WARN` (0.65) and calls it a duplicate at ≥ `JACCARD_DUPLICATE` (0.85); `findSimilar` reports from `JACCARD_SIMILAR` (0.50); cosine matches at ≥ `COSINE_MATCH` (0.45). Pass front and back to `findSimilar` so its embedding compares like with like.


## Lint Rules to Know

- `strict-boolean-expressions` (warn): No implicit truthy checks on strings/numbers. Use explicit `!== ""`, `!== 0`, `!= null`.
- `no-floating-promises` (error): Must `await`, `.catch()`, or `void` all promises.
- `consistent-type-imports` (error): Use `import type { Foo }` or `import { type Foo }`.
- `eqeqeq` (error, null-exempt): Use `===`/`!==` except for `== null` / `!= null`.

## Test-First Workflow

Write tests before implementation. Tests use a fresh temp SQLite DB per suite (see `__tests__/setup.ts`). Test files mostly mirror source structure: `__tests__/core/scheduler.test.ts` tests `src/core/scheduler.ts`; cross-cutting behaviour gets its own file (`tombstones.test.ts`).

## Debugging (omp)

TypeScript LSP comes from the `typescript-language-server` devDependency (omp finds it in `node_modules/.bin`). `.omp/dap.json` points omp's `js-debug-adapter` at `tsx` (`--import tsx`), so `debug launch` on a `.ts` entry point (e.g. `src/cli/index.ts`) stops on entry with source-mapped breakpoints; it needs vscode-js-debug's `dapDebugServer.js` at `~/.local/opt/js-debug/src/` (or `JS_DEBUG_DAP_SERVER`).
